# arctic owns the OAuth lifecycle; vendor SDKs only make API calls

Neither official SDK can be the OAuth client on Workers. `@azure/identity` keeps the refresh token in an in-memory MSAL cache that `getToken()` never exposes and an isolate cannot outlive, so the refresh cycle cannot be sustained. `google-auth-library` overwrites a rotated refresh token with the stale one it sent, silently destroying the Credential. Both were verified against package source and a local workerd harness, not just documentation. So `arctic` performs authorize, code exchange and refresh for both Providers, while `@googleapis/calendar` and the Microsoft Graph SDK are used only for API calls with an externally supplied access token.

**Consequences.** `arctic` does not add Google's `access_type=offline` or `prompt=consent`, so the authorize URL is patched before redirect — without it Google issues no refresh token at all. Microsoft's scope list must carry `offline_access` explicitly. The Google client needs `globalThis.window = globalThis` (otherwise gaxios loads `node-fetch`) and an auth adapter exposing `request(opts)`, because googleapis-common calls `authClient.request`, not just `getRequestHeaders`; a string `auth` would be read as an API key. Graph needs `@microsoft/msgraph-sdk-users` imported for its `me.onenote` registration and every `@microsoft/kiota-*` pinned to one preview number.

**Considered Options.** Delegating token lifecycle to the vendor SDKs was the obvious path and fails for the reasons above. Plain `fetch` for both Providers would remove ~900 KiB of bundle, but loses typed request building and per-Provider pagination that the SDKs already model; the gateway keeps the SDKs and accepts the shims.
