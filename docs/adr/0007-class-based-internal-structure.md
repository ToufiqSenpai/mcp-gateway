# Class-based internals behind thin contract adapters

The codebase began with closure factories: `createMcpContext`, `createEnumerationCache`, `createCursorCodec`, `googleCalendar`, `graphClient` and `defineTool` each returned an object literal of closures. That kept the module boundary small, but it hid object lifecycles and made stateful collaborators — Provider clients, refresh locking, credential encryption, the Account repository — read as free functions taking the same dependencies repeatedly.

**Decision.** Stateful collaborators are classes: Provider clients, `AccountRepository`, `AccountService`, `RefreshService`, `OAuthFlowService`, `TokenCipher`, `AccessVerifier`, `EnumerationCache`, `HmacCursorCodec`, `ToolContext`, `ToolRegistry`, the resource and prompt registries, `McpRegistry`, and `InProcessRunner`. Pure mappers, Zod schemas, URI encoders, cookie helpers and JSX views stay functions. Tool and prompt declarations stay top-level data in `tools/index.ts` and `prompts.ts`: their array order is the wire order, and wrapping each declaration in a class would add boilerplate without adding state.

The documented boundary is unchanged. Each MCP package exports its server class (`CalendarServer` / `NotesServer`), and `MCP_REGISTRY` builds one per request; `McpContext` is still a structural interface, and `GatewayMcpContext` implements it without adding members. `AccountRepository` and `OAuthStateRepository` each take `env` and own their D1 handle.

**Consequences.** Every class that holds `env`, `db` or `ctx` is constructed per request; no module-level singleton holds request state. The per-isolate performance caches that remain (imported AES key, JWKS sets) are static class fields with a comment, not request state. Tests can construct a class directly (`new TokenCipher(key)`, `new HmacCursorCodec(secret)`, `new AccessVerifier(env)`) instead of calling a factory. Tool order, JSON schemas, `ToolResult` `instanceof` handling and error identities are unchanged, so the wire contract and the conformance tests stay valid. The structural `Same<A, B>` test still fails the build if a class widens `McpContext`.

**Considered Options.** Staying fully functional was the lowest-churn option, but it left refresh locking, encryption and Account selection as long functions with repeated parameters. A dependency-injection container would make lifetimes explicit but adds a framework to a single Worker with one composition root. A shared `mcp-kit` package for the duplicated tool framework would remove about 150 lines of duplication but couples the two MCP packages and needs its own workspace package and ADR; the duplication is accepted for package independence.
